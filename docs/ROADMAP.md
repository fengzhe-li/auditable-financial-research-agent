## Failure injection cases

Built out in Phase 6; defined here so earlier phases can design against them from the start.

- Missing filing
- Stale document
- Irrelevant retrieval
- Conflicting evidence
- Malformed tool output
- Tool timeout
- Empty retrieval
- Token-budget exhaustion
- Unavailable model
- Policy violation
- Restricted-data exposure attempt
- Prompt injection (see the specific attack cases in [docs/THREAT_MODEL.md](THREAT_MODEL.md#indirect-prompt-injection))

Expected behaviour for every case above is a safe, legible failure (a specific state, a specific `SecurityEvent`, or a specific error) — never a fabricated success.

## Design review before Phase 1

Phase 1 does not start until the Phase 0 documentation set is internally consistent — see the review at the end of this repository's setup: the proposed repository tree, an architecture summary, and an explicit list of anything too broad, incoherent, or overengineered in this design, with a recommendation for the smallest Phase 1 slice that actually proves the core idea (evidence-grounded claims + a real, enforced state machine — not the full system).

## Recording deviations

If a later phase's implementation reveals that something in Phase 0's design doesn't hold up (a component that turned out to be unnecessary, a state transition that didn't match real usage, a policy abstraction that was over-engineered for what was actually needed), record it here against the relevant phase rather than silently diverging from the documented design or silently editing the earlier docs as if they'd always said the new thing. The documentation should show its own history of being wrong sometimes, not just its final state.

**Phase 1 (recorded 2026-09-16):** [docs/ARCHITECTURE.md](ARCHITECTURE.md) names PostgreSQL as the data layer. Phase 1 persists to SQLite instead — real, on-disk, process-restart-durable storage, sufficient to prove the resumability requirement, without pulling in a Postgres server/Docker dependency for a vertical slice that doesn't yet need relational query complexity. The schema is written to map cleanly onto the documented entities so a later Postgres migration (Phase 8) is a storage-layer swap, not a schema redesign. This is a deliberate, scoped substitution, not a silent architecture change.

**Phase 2 (recorded 2026-09-16):** Two corrections to Phase 1, plus one addition beyond the original entity list:

- Phase 1's `get_document()` actually behaved like `retrieve_section()` (fetched section text and produced `Evidence`) — a role conflation that only became visible once Phase 2 needed a real `get_document()` (metadata lookup) and `search_documents()` (candidate discovery) to exist alongside it. Corrected: `get_document()` is now a pure metadata lookup with no `task_id` and no `Evidence` output; the evidence-producing logic moved to `retrieve_section()`, matching [docs/ARCHITECTURE.md](ARCHITECTURE.md#controlled-tool-layer)'s original tool definitions. The orchestrator's public `gather_evidence_from_document()` method name and signature were kept unchanged for Phase 1 test compatibility; it calls `retrieve_section()` internally.
- `search_filings()` from [docs/ARCHITECTURE.md](ARCHITECTURE.md) is implemented as `search_documents()` in code — a naming choice made when writing the tool, not a deliberate rename with a rationale; the architecture doc has not been changed to match, since this project's own documentation practice is not to silently edit earlier docs (see this section's header). Treat `search_documents()` as the authoritative name going forward.
- Two audit tables not in the original [docs/CLAIM_EVIDENCE_MODEL.md](CLAIM_EVIDENCE_MODEL.md) entity list — `ToolCall` and `StateTransition` — were added, following the same pattern as `ModelCall`. These exist because Phase 2 explicitly requires tool calls and state transitions in the persisted trace; they have no reader yet beyond `afra.trace.assemble_trace()` and the Phase 2 report's example script. If Phase 7 (frontend) doesn't end up needing anything beyond what `Evidence`/`Claim`/`ModelCall` already provide, these two tables should be reassessed rather than assumed permanent.

**Phase 3 (recorded 2026-09-16):**

- **Behaviour change, not a bug fix:** a claim with `support_status == CONFLICTING_EVIDENCE` now fails `evaluate_sufficiency_and_advance()` (routes the task to `INSUFFICIENT_EVIDENCE`) instead of passing through to `AWAITING_REVIEW` as it did in Phase 2. Rationale: Phase 2's design let a human reviewer see and resolve a conflict a human analyst had deliberately constructed; Phase 3's router discovers conflicts autonomously, and handing an unresolved, autonomously-discovered contradiction to a reviewer as if it were an ordinary draft doesn't fit "humans approve, they don't triage the system's confusion." The corresponding Phase 2 test (`test_conflicting_evidence_does_not_become_supported`) was updated in place to assert the new behaviour, with the change explained in its docstring, rather than left to silently diverge from what it once tested.
- `ResearchScope`'s four non-material fields (`time_range`, `document_types`, `source_constraints`, `source_scope`) are always defaulted to `RESOLVED` with a fixed value, never actually interpreted from the question text. This is an honest scope-discipline call, not an oversight: the fixture corpus has exactly one document type and no internal-source concept yet, so building real interpretation logic for these fields would have nothing to be tested against. Revisit when Phase 4 (classification) or a richer corpus gives these fields something real to resolve.
- No new audit table was added for routing decisions - they're persisted as `ToolCall` rows with `tool_name="route_subquestion"`, reusing Phase 2's table rather than adding a third one (see the Phase 2 entry above about watching table growth).

**Phase 4 (recorded 2026-09-16):**

- **New state transition, not in Phase 0's original table:** `SYNTHESISING` → `SECURITY_BLOCKED` (see [docs/STATE_MACHINE.md](STATE_MACHINE.md)). Phase 0/1-3 only documented `VALIDATING` → `SECURITY_BLOCKED`, implicitly assuming policy enforcement would run after validation. It actually has to run *before* the one model call that exists (claim drafting, in `SYNTHESISING`) - checking after the model has already been called would be too late to prevent the call itself. `VALIDATING` → `SECURITY_BLOCKED` remains in the transition table but is unreached by any implemented code path in Phase 4 - kept for a possible future check on content leaving the system boundary at/after validation.
- **`require_approval` currently behaves identically to `block` in its effect on task state.** [docs/DATA_CLASSIFICATION.md](DATA_CLASSIFICATION.md) documents `require_approval` as "a human (compliance/governance reviewer) must explicitly approve before the content proceeds," implying a resumable, distinct path. No approval-resolution workflow exists yet (it is Phase 5 scope: "Full human review / approval workflow" already lists review-workflow extension as future work). In Phase 4, both `block` and `require_approval` transition `SYNTHESISING` → `SECURITY_BLOCKED` and raise `SecurityPolicyError` identically; the *only* place the two are currently distinguished at all is the `action_taken` value recorded on the persisted `SecurityEvent`. This is an honest scope gap, not a design decision to treat them as equivalent long-term.
- **The publication gate's SecurityEvent clause, documented in Phase 0's [docs/CLAIM_EVIDENCE_MODEL.md](CLAIM_EVIDENCE_MODEL.md#publication-gate) but explicitly marked "trivially passes" in the Phase 1-3 implementation (no SecurityEvent rows could exist yet), is now real**: `evaluate_publication_gate()` fails if any unresolved (`resolved_by is None`) SecurityEvent for the task has `action_taken` in `{block, require_approval}`. In practice this clause is not reachable via any orchestrator-driven path in Phase 4 (a blocking decision during drafting already prevents the task from ever reaching `APPROVED`), so it is currently proven only by a direct, hand-constructed repository test (`test_unresolved_blocking_security_event_blocks_publication_even_if_claim_is_supported`), the same pattern already used for the gate's other clauses.
- Prompt-injection defence is architectural, not pattern-based: the deterministic test-double providers (`afra.providers.test_double`) parse retrieved text as fixed-format data and never "obey" embedded instructions, so injected text cannot change `support_status`, routing, or trigger a tool call regardless of whether the DLP scanner's `prompt_injection_pattern` regex happens to match it. That pattern category exists purely as an audit signal (visible in the persisted `SecurityEvent.detected_categories`), and is explicitly documented (`afra.policy.dlp` module docstring) as not being the actual defence, to avoid overstating what a regex match proves.
- Only one call site (`_draft_and_persist_claim`) currently goes through `afra.policy.enforcement`. Evidence retrieval itself (`retrieve_section`) is not policy-gated - a document's classification is attached and inherited correctly, but nothing currently stops an analyst from retrieving `RESTRICTED` evidence into a task; enforcement only blocks the point where that evidence would reach a model. Extending enforcement to the retrieval boundary itself (e.g. requiring elevated access to even call `retrieve_section` on `RESTRICTED` documents) is deferred, not silently assumed to be covered.

**Phase 5 (recorded 2026-09-16):**

- **New terminal state, not in Phase 0's original 13-state list:** `TaskState.REJECTED`, reachable from `AWAITING_REVIEW` via a new `ReviewDecision.REJECT`. Phase 0 only defined `approve`/`request_revision`; the Phase 5 spec explicitly required a hard-rejection outcome distinct from the resumable revision cycle, so this needed its own terminal state (mirroring `SECURITY_BLOCKED`'s terminal philosophy for a content/quality reason rather than a security one) rather than overloading `REVISION_REQUESTED` or `FAILED` (which is documented as an *operational* failure, not a reviewer decision on the merits).
- **Reviewer separation (`reviewer_id != created_by`) now applies to every review decision, not only `approve`.** Phase 1-4 only checked self-approval; a self-`REJECT` or self-`REQUEST_REVISION` was legal. Phase 5 broadens the check to all three decisions, since separation of duties is about the reviewer *role* being distinct from the author, independent of what they decide. No existing test relied on the narrower behaviour, so this is a pure strengthening, not a breaking change.
- **A new "reviewer is authorized" check, `afra.identity.AUTHORIZED_REVIEWER_IDS`, was added** - a small, fixed, in-code allow-list (`reviewer_1`, `governance_admin`), enforced both in `submit_review()` and independently in the publication gate. This narrows one sentence of Phase 1's original identity-scope documentation, which said "who is allowed to act as `governance_admin` versus `analyst_1` ... is a deployment/configuration concern this project does not address." The Phase 5 spec explicitly required "reviewer is authorized" as a publication-gate condition distinct from "reviewer is not the task author," which the Phase 1 wording alone could not satisfy - so this is a recorded, deliberate narrowing, not a silent contradiction of the earlier text. It remains local/fixture-based and explicitly not authentication - see the Phase 5 addendum in [docs/CLAIM_EVIDENCE_MODEL.md](CLAIM_EVIDENCE_MODEL.md#identity-scope-portfolio-implementation).
- **`Review.comments` was kept, not renamed to "rationale"** (the field name used in the Phase 5 spec's illustrative field list), to avoid breaking every Phase 1-4 call site and test that already constructs a `Review` with `comments=`. It serves the same role; see [docs/CLAIM_EVIDENCE_MODEL.md](CLAIM_EVIDENCE_MODEL.md#review)'s field table.
- **`ResearchTask.claim_set_version` is a simple monotonic integer counter** (incremented on every `complete_synthesis()` call), not a content fingerprint/hash of the claim set. It correctly detects "the claim set was finalised again since this approval" but would not, on its own, distinguish two different claim sets that happened to be finalised the same number of times across two different tasks (not a real concern, since the check is always scoped to one task's own version history) or catch a claim mutated in place *without* going through `complete_synthesis()` again (not currently possible via any orchestrator method - claims are never mutated after creation except by `record_validation_result()`, which does not touch `claim_text`). Chosen for simplicity over a hash-based fingerprint, consistent with this project's stated anti-overengineering discipline; revisit if a future phase adds any in-place claim mutation.
- **`resolve_security_event()` is real but deliberately inert with respect to task state.** The Phase 5 spec required "the real workflow that resolves" a `require_approval` block "through an authorized human review," while also requiring that "a normal reviewer approval must not bypass a security block unless the existing spec explicitly defines a governance override path" and that no such override be invented if none exists. No override path exists in `docs/STATE_MACHINE.md` (`SECURITY_BLOCKED` has zero outgoing transitions, by design, from Phase 4). Resolving an event reconciles both requirements: `resolved_by` is genuinely set, satisfying the publication gate's own SecurityEvent clause for that specific event - but the task itself remains `SECURITY_BLOCKED` and unreachable from any orchestrator method, so this can never become a live path to `PUBLISHED`. Restricted to `block`-vs-`require_approval` distinction: a `block` decision has no resolution path at all (raises `SecurityPolicyError` if attempted), since this project defines no human-override concept for an outright block.
- **No "memo" or "required-claims subset" concept was added in Phase 5**, despite the revision loop conceptually raising the question of whether a reviewer's `REQUEST_REVISION` should be able to supersede/retire a specific prior claim rather than only add new ones alongside it. This is the same Phase 1 simplification carried forward unchanged (every `Claim` belonging to a task is still treated as required by the publication gate) - see the Phase 1 entry above. Building a real "supersede a claim" concept was judged out of Phase 5's explicit scope (no new tools, no new memo abstraction) and is left for whichever future phase actually needs it.

**Phase 6 (recorded 2026-09-16):**

- **Only A, D, and F were built, per this phase's own instruction** ("Do not implement B/C/E unless the first three configurations reveal a specific need for finer ablation"). They didn't reveal such a need - see [PHASE_6_REPORT.md](PHASE_6_REPORT.md)'s §4 for the full per-metric breakdown of what A/D/F could and couldn't separate on their own.
- **Configuration D, as actually implemented, necessarily includes Phase 4's policy enforcement**, even though the Phase 6 spec described D as having "no full security/governance layer." Phase 4 wired `afra.policy.enforcement` unconditionally into the one shared claim-drafting code path (`_draft_and_persist_claim`), and Phase 6 was explicitly told not to weaken existing invariants to improve ablation cleanliness. Resolution: D's benchmark task scope excludes the `sensitive_data_routing_policy` category entirely (`afra.benchmark.schema.CONFIGURATION_D_EXCLUDED_CATEGORIES`) rather than pretending to measure something this codebase cannot structurally produce. D *is* evaluated on `prompt_injection` tasks, since injection resistance here is architectural (shared by every configuration that uses the real orchestrator), not specific to the Phase 4 policy layer - a real, disclosed distinction between what D lacks and what it doesn't.
- **Configuration D's actual distinguishing property, matching Phase 0's original ablation ordering** (`docs/EVALUATION_PLAN.md`: "D = C + validator", "E = D + abstention"), **is that it stops after `run_validation()` and never calls `evaluate_sufficiency_and_advance()`, `submit_review()`, or `publish()`** - composed from existing public `ResearchTaskOrchestrator` methods, not a new orchestrator code path. This was not explicit in the Phase 6 spec's bullet list for D but is the only implementation consistent with both "no abstention" (implied by contrast with F, which does list "sufficiency / abstention") and "do not implement E" (abstention was E's addition in the original ordering, never D's).
- **A genuine router limitation was discovered while building this benchmark**: `afra.routing.router.pick_latest_document()` selects purely by `published_at` date with no document-type awareness, which made the `conflicting_evidence` and `sensitive_data_routing_policy` categories structurally unreachable via unmodified autonomous routing (every INTERNAL/CONFIDENTIAL/RESTRICTED fixture document is dated earlier than the same company's latest 10-K). **Phase 6.5 rate-limit patch (recorded 2026-09-19, after the provider migration above):**

- **The disclosed gap in the entry above was hit for real.** A first live smoke test (`--live --configurations F --repeat 1`) reached the real Gemini API and made several successful calls, then failed with an unhandled `429 RESOURCE_EXHAUSTED` - the observed Free Tier quota is 5 requests/minute/project/model. Because no retry/backoff existed yet, the exception propagated all the way out of `live_run()` and the run never reached the point of writing `manifest.json` - a crash, not a normal `rate_limited` task result. No canonical A/D/F ×3 experiment was attempted; this was the optional one-off smoke test only.
- **Fix: pacing + bounded retry/backoff, entirely inside `GeminiClaimDraftProvider`.** `complete()` now paces itself at least `min_call_interval_seconds` (default 15s, configurable, `--min-call-interval-seconds` on the CLI) after its own previous real network attempt before making another one - separate draft_claim calls never come closer together than that. A 429 within one `complete()` call is retried up to `max_retries` times (default 3, `--max-retries` on the CLI), honouring the server's own `RetryInfo` retry delay (or an HTTP `Retry-After` header) when present, otherwise a bounded exponential backoff (10s/20s/40s, capped at 60s) - see `afra.providers.real_model._generate_with_retries`/`_pace`/`_parse_retry_delay_seconds`. None of this touches `afra.providers.test_double.TestDoubleProvider` or any deterministic path at all - verified by `tests/test_real_model_harness.py::test_deterministic_test_double_provider_has_no_pacing_or_retry_state` and `::test_deterministic_benchmark_is_unaffected_by_the_rate_limit_patch`.
- **If every retry is exhausted, the failure is now recorded, not crashed on.** `RateLimitExhaustedError` is caught per task by `afra.benchmark.real_model_harness._run_repeat()`, the same way `IncompleteCompletionError` already was - persisted as `"status": "rate_limited"` (no `"result"`/`"score"` key, so it can never be mistaken for a graded outcome) and rolled up into the run manifest's new `rate_limited_attempts` count. A third, broader catch-all (`"status": "provider_error"`, `provider_error_attempts`) was added at the same call site for any other real-provider failure (a different API error, a network failure, ...) that isn't a rate limit or an incomplete completion - so a single bad attempt of *any* kind can no longer take down the rest of a paid live run.
- **New observability fields, recorded where available on every task result, not only failed ones**: `latency_ms`, `token_usage`, `retry_count`, `rate_limit_events` (each with `attempt`/`delay_seconds`/`source`/`status`), and a final `provider_status` (`"ok"`/`"incomplete"`/`"rate_limited"`/`"unknown"`) - nested under each task JSON's new `"observability"` key, read via `getattr(provider, "last_*", None)` so a deterministic test-double provider that doesn't set them never breaks the harness.
- **24 new tests added** (`test_real_model_harness.py`, 47 → 71), all using injected fake `sleep_fn`/`clock_fn` and a fake SDK exception carrying the real `google.genai.errors.ClientError`'s `code`/`status`/`details` shape - zero real network calls and, new for this patch, zero real `time.sleep` (mechanically checked by `test_no_real_sleeping_occurs_across_a_full_retry_and_pacing_scenario`, which asserts a scenario that would take 45 real seconds under `time.sleep` completes in under 1 second of actual wall-clock time). Full backend suite: 258/258 pass.
- **Frozen 14-task subset, A/D/F semantics, `afra.benchmark.grader`, gold labels, Phase 4 policy enforcement, and the canonical `repeat=3` experiment design are all unchanged** - this patch only ever touches `afra.providers.real_model` (pacing/retry inside `GeminiClaimDraftProvider`) and `afra.benchmark.real_model_harness` (catching the two new exception types per task and writing richer, but never fabricated, task-result JSON).

See [PHASE_6_5_REAL_MODEL_REPORT.md](PHASE_6_5_REAL_MODEL_REPORT.md)'s status section for the exact commands, unrun as of this entry.

**Benchmark-analysis layer (recorded 2026-09-19, independent of Phase 6.5 - `afra.providers.real_model`, `afra.benchmark.real_model_harness`, `backend/scripts/run_real_model_benchmark.py`, Gemini configuration, live result directories, the frozen task definitions, A/D/F execution semantics, `afra.benchmark.grader`'s scoring rules, and Phase 4 policy enforcement were all untouched by this entry's work):**

- **Deepens interpretation of existing benchmark results without changing the underlying experiment.** Two new modules, `afra.benchmark.analysis` (Wilson confidence intervals, repeat variance, denominator-sensitivity/model-quality-vs-infrastructure separation, run comparison) and `afra.benchmark.failure_taxonomy` (a deterministic outcome classifier distinguishing infrastructure failures from gradable outcomes), plus a thin file-reading layer (`afra.benchmark.report`) that applies both to on-disk run artifacts - see [docs/BENCHMARK_ANALYSIS.md](BENCHMARK_ANALYSIS.md) for the full design and statistical rationale.
- **`afra.benchmark.aggregate`'s per-category breakdown had a real, silent gap, closed here**: `by_category` only ever reported 5 of the 9 metrics [docs/EVALUATION_PLAN.md](EVALUATION_PLAN.md#metrics) defines - `retrieval_recall`, `citation_precision`, and `leaked_restricted_content_rate` were entirely absent per-category, even though the top-level aggregate always had them and every D/F task computes them. Fixed by driving both the top-level aggregate and `by_category` from one shared metric list (`_BOOL_METRICS`/`_FLOAT_METRICS`), so the two categories of reporting can no longer drift apart. This is the one change to `afra.benchmark.aggregate` itself (a reporting/rollup module, not the grader); `afra.benchmark.grader.grade_task()` - the actual per-task scoring logic - was not touched.
- **Wilson intervals, not Wald, and only for genuine binomial-proportion metrics.** Applied to `completion_rate`/`abstention_accuracy`/`clarification_accuracy`/`prompt_injection_attack_success_rate`/`policy_block_accuracy`/`leaked_restricted_content_rate` only - `retrieval_recall`/`citation_precision`/`unsupported_claim_rate` are means of a per-task fraction, not a binomial count, and deliberately get no CI (a mean and its `n`, reported honestly, rather than a statistically inappropriate interval bolted on). Two entry points: `with_confidence_intervals()` (exact, from raw `TaskScore`s) and `with_confidence_intervals_from_summary()` (from an already-persisted `aggregate.json`, recovering successes as `round(value*n)` - the common case for analysing historical results with no raw scores in hand).
- **Repeat variance never invents a standard deviation for a single repeat** - `stdev` is `None`, not `0`, when only one repeat exists (sample stdev is undefined at n=1; reporting 0 would falsely claim measured reproducibility that was never tested).
- **Model-quality vs. infrastructure separation was already correct structurally** (`real_model_harness._run_repeat()` never appended a rate-limited/provider-error/incomplete attempt to what it grades, before this entry existed) - this layer makes that separation *visible* in a report (`model_quality_report()`'s explicit `total_attempted`/`graded`/`infrastructure_failures` breakdown) and adds `denominator_sensitivity()`, which shows each metric under both the existing graded-only framing and a deliberately conservative "every non-graded attempt counted as a failure" framing, side by side - never merged into one number, and never imputing a score for a task that didn't run.
- **`compare_runs()` reports evidence, never a verdict** - deltas, `n`s, and confidence-interval overlap at both aggregate and category level, worded as "evidence of a real difference" / not flagged, never as "replicates" or "fails to replicate". Demonstrated end-to-end against Phase 6's own real deterministic results (`run_f3bb065c08c9`'s D vs. F aggregates, read-only): `abstention_accuracy`'s confidence intervals do not overlap (D: 0.72 n=39, F: 1.00 n=42) - genuine, CI-confirmed evidence F's abstention gate works, surfaced without a single invented number.
- **76 new backend tests** (`test_benchmark_aggregate.py`, 6; `test_benchmark_analysis.py`, 43; existing benchmark test files otherwise unchanged) covering Wilson-interval correctness against a known reference value and the zero-n/extremes edge cases, repeat aggregation (including single-repeat and a metric missing from some repeats), infrastructure failures excluded from model-quality denominators, the full failure taxonomy, per-category aggregation, run comparison (including the "never returns a verdict" invariant), and single-repeat edge cases end-to-end through a hand-built fake run directory.
