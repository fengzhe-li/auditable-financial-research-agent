# Phase 2 Report

Status: **Complete.** 52/52 tests pass (`cd backend && python3 -m pytest -v`), up from 30 at the end of Phase 1.

## The Phase 2 success criterion

> A bounded financial research question can be decomposed, evidence can be gathered from multiple documents, claims can be drafted, and unsupported claims still cannot pass the existing assurance gates.

Proven end-to-end by `backend/tests/test_phase2_end_to_end.py::test_full_bounded_comparison_task_reaches_published`, for the representative task:

> *"Compare how Contoso Cloud Corp and Fabrikam Systems Inc describe AI infrastructure investment risk across their latest two annual reports."*

(Contoso and Fabrikam are the same fictional companies from Phase 1's fixture corpus, now each with two filing years so a genuine two-document, temporal comparison is possible.)

## The end-to-end state path (real, exercised by the test above)

```text
CREATED
  → PLANNING              (create_task)
  → GATHERING_EVIDENCE    (run_planning: 3 subquestions produced)
  → SYNTHESISING          (complete_evidence_gathering: 2 evidence items retrieved)
  → VALIDATING            (complete_synthesis: 3 claims drafted)
  → AWAITING_REVIEW       (evaluate_sufficiency_and_advance: all 3 claims SUPPORTED)
  → APPROVED              (submit_review: reviewer_1 approves, reviewer_1 != analyst_1)
  → PUBLISHED             (publish: gate re-checked and passes)
```

Every arrow above is a real, persisted `StateTransition` row, not a description — see the trace excerpt below.

## What's real

- **The minimal planner** (`afra/planning/planner.py`): a real call through the provider abstraction, a real parsed 2–4 subquestion output, a real `PlanningError` safe-failure path, and a real `ModelCall` audit record for both the success and failure case.
- **All three tools** (`search_documents`, `get_document`, `retrieve_section`): real code, real fixture-corpus lookups, real `Evidence` provenance (document identity, section location, timestamp, content hash, classification), and every call is now a real, persisted `ToolCall` audit record.
- **Evidence-driven claim drafting** (`draft_claim_from_evidence`): the prompt sent to the provider is built from real retrieved `Evidence` text, not an arbitrary caller-supplied string (Phase 1's `draft_claim` still exists and is still used directly by three of the five Phase 2 failure-case tests, where a deliberately malformed or mixed-support citation needed to be constructed by hand).
- **The invariant that drafting never sets `support_status`/`support_strength`/`approval_status`** — structurally true, not just documented: those fields do not appear anywhere in `afra/synthesis/claim_drafting.py` or in `draft_claim_from_evidence`'s body. They are set in exactly one place, `Repository.record_validation_result()`, unchanged since Phase 1.
- **The full state path** shown above, for a genuine two-company, two-evidence-item, three-claim, one-multi-evidence-claim comparison task.
- **`ToolCall` and `StateTransition`** as real, queried, persisted audit tables — not just declared. `afra.trace.assemble_trace()` (one small pure function, ~100 lines, no service layer) reads all of `ResearchTask`, `Evidence`, `Claim`, `ClaimEvidenceLink`, `ValidationResult`, `Review`, `ModelCall`, `ToolCall`, and `StateTransition` into the structure shown above.
- **All five required failure cases**, each with a passing test: planner safe-failure, no-relevant-evidence → `INSUFFICIENT_EVIDENCE`, no-evidence-link claim blocked, conflicting evidence does not become `SUPPORTED` (proven via genuinely conflicting real fixture text — 2024 "do not currently expect a material increase" vs. 2025 "expect ... to increase materially" — not a synthetic example), and unsupported claims still cannot reach `PUBLISHED`.

## What's fixture / test-double based

- **The fixture corpus is still entirely fictional** — now 4 documents (2 companies × 2024/2025) instead of Phase 1's 2, still invented text, not real filings.
- **The planner's "intelligence" is a deterministic prompt-parsing trick, not reasoning.** `TestDoubleProvider._plan()` extracts a `"Known companies in scope: X, Y"` line from the planner's fixed prompt format and fills a template. It cannot decompose an actual free-text question about unfamiliar topics — it can only reliably decompose the exact structured prompt shape `build_planning_prompt()` produces. A real provider adapter (Phase 3+) would be needed to prove decomposition works on genuinely varied input.
- **Claim text is the test-double's literal echoed prompt** (visible in the full trace, trimmed above), not a natural-language claim a person would write. The *mechanism* (claim drafted from real evidence, support computed independently) is real; the *prose quality* is not attempted in Phase 2.
- **`search_documents()` is exact case-insensitive substring matching**, not search in any real sense — no ranking, no relevance scoring, no fuzzy matching.

## What remains deferred

- The remaining 6 tools (`retrieve_evidence`, `compare_sections`, `build_evidence_table`, `validate_citations`, `check_claim_support`, `generate_research_memo`) — Phase 3.
- Real ambiguity detection in the planner (Phase 2's planner decomposes an already-bounded question; it does not decide whether a question needs clarification in the first place — that's still `request_clarification()` called directly, as in Phase 1) — Phase 3.
- **Autonomous tool-call selection.** This is the most important boundary to be honest about: the planner returns subquestion *text*. Nothing in this codebase decides, on its own, that subquestion 1 should be answered by retrieving `CONTOSO-2025-10K#risk_factors` specifically (as opposed to the 2024 filing, or Fabrikam's). That mapping is supplied by the caller — currently, tests. A real system would need a controller loop that reads a subquestion, calls `search_documents()`, picks a result, calls `retrieve_section()`, and decides when it has enough evidence to draft a claim. None of that exists yet. See [Overengineering flags](#overengineering-flags) below for why this wasn't built now.
- A real external model provider adapter, data classification enforcement, DLP, the frontend, Docker, the benchmark — unchanged from Phase 1's deferred list.

## Overengineering flags

1. **The tool-wrapper pattern will want an abstraction it doesn't have yet — but not yet.** Each of the 3 tools this phase added required three pieces: a pure function (`afra/tools/*.py`), an orchestrator wrapper method that logs a `ToolCall`, and (for `retrieve_section`) a state guard. Repeating this by hand for the remaining 6 tools in Phase 3 will produce real, visible boilerplate. A small dispatch/registry abstraction (e.g. a decorator that wraps a tool function with audit-logging and state-checking) would remove that duplication — but building it now, for 3 tools, would be solving a problem that doesn't exist yet. The right trigger for adding it is when the 4th or 5th tool makes the copy-paste undeniable, not speculatively now.
2. **`ToolCall` and `StateTransition` are two new tables with exactly one reader each** (`assemble_trace()` and this report's example script). They were explicitly requested and follow an existing pattern (`ModelCall`), so I didn't hold them back — but they're worth watching: if Phase 7's frontend ends up not needing anything beyond what `Evidence`/`Claim`/`ModelCall` already expose, these should be reconsidered rather than assumed permanent by default. Recorded in [docs/ROADMAP.md](ROADMAP.md#recording-deviations).
3. **`known_companies` must be supplied by the caller to `run_planning()`.** The system does not extract "Contoso Cloud Corp" and "Fabrikam Systems Inc" from the free-text question itself — it needs to already be told. This is not a bug I'm flagging for a fix; it's the actual, honest boundary of what "decomposition" means in this phase, and I'd rather state it plainly than let the success criterion's passive phrasing ("can be decomposed") imply more autonomy than exists. Building real entity extraction now, ahead of a second real use case to design it against, would be premature.

None of the above blocks Phase 3 - they're recorded so Phase 3 doesn't have to rediscover them.
